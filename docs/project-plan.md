## 1. 项目定位

**一句话：具身智能（机器人）多传感器数据的"翻译官 + 质检员"。**

机器人身上挂着摄像头、深度相机、IMU、关节、力传感器，它们各说各话：时间戳不同步、
单位不统一、坐标系各异、有的数据是坏的。上层模型需要符合其输入契约的数据；
有些模型直接消费图像，有些还需要状态、动作或空间信息。
EmbodiedSense 做中间那一步：把各种传感器的数据收进来，对齐时间、统一单位和坐标系、
检查质量，输出一份干净、统一、带体检报告的数据。

**它现在是工具，目标是平台，但平台是结果不是起点。** 一个人先把一件事做得真正好用，
别人才可能围着它做东西，那时候才叫平台；一上来就宣称"做平台"是空的。

**"专用"专在哪：** 通用数据处理工具（给电商、金融用的）处理不了机器人数据，
因为机器人数据有三个它自己的麻烦——多个传感器时间戳要互相对齐（容差取决于采样率、运动和任务）、
单位和坐标系不统一就无法计算、数据要和机器人动作对齐（这帧画面时机械臂在干什么）。

### 1.1 长期架构原则：能力边界保持完整，当前范围保持窄

本项目的**当前范围**对准"数据可信 + 工具互操作"这一条链路（见 §5、§6），
但这是**阶段性选择，不是永久定位**。架构上必须始终保留下面四个能力，
当前阶段只是把其中一条做深：

| # | 能力 | 当前状态 |
|---|---|---|
| 1 | **Data Ingestion & Processing**：多模态数据接入、同步、坐标与单位统一 | MVP 1 已实现（RGB-D 链路） |
| 2 | **Data Quality & Validation**：异常检测、完整性校验、统一报告 | MVP 1 已实现基础版，下一步做跨工具统一 |
| 3 | **Data API & SDK**：**既要返回质量检查报告，也要提供处理后的传感器数据** | 部分实现（Python API / CLI），需显式补齐（FR-12） |
| 4 | **Agent / MCP Integration**：让 DeepSeek 等 Agent 直接调用数据服务 | 可选阶段 P4 |

**第 3 条是这条原则的关键**：如果 API 只返回"体检报告"而不返回"处理后的数据"，
项目会逐渐退化成"一个生成质量报告的工具"，失去最初设想的数据服务能力。

AI 感知、三维场景理解、SLAM、嵌入式部署留到后续版本，但**架构上不为它们设障**。

## 2. 背景与动机

### 2.1 具身智能数据的三类真实问题

1. **时间错位**：RGB 30 Hz、IMU 200 Hz、关节 100 Hz，各自时钟起点不同，直接混用会训坏模型。
2. **质量不可知**：深度图无效像素、模糊/黑帧、丢帧乱序、NaN、标定缺失，出了问题排查极慢。
3. **坐标系混乱**：相机光学坐标、机器人基座、世界坐标，不统一就没法做几何计算。

### 2.2 为什么这件事值得做（有实测依据，不是推测）

2026-10-11 的实测（`docs/toolchain-integration-matrix.md`）：对同一份**注入 8 种已知故障**
的多模态数据，现成质检工具的表现是——

| 工具 | 检出 | 说明 |
|---|---|---|
| physlint 0.3.2 | **0 / 8**（拆解见下） | 干净数据与故障数据的 18 条规则状态+消息**逐条完全一致** |
| embodied-sync 0.1.3 | **1 / 8，且漏报** | 报 cam_front 缺 1 帧，注入真值是 7 帧 |
| bagx 0.6.0 | 未测 | 需要 rosbag2 输入 |
| hflow 0.2.21 | 无法运行 | Windows 下缺 `fcntl`（Linux-only） |

**原因不是工具差，是交接坏**：导出时整条相机流被丢掉（7 条流变 3 条）、流命名不匹配
（`actions`/`robot_state` vs 下游要的 `action`/`observation.state`）导致干净数据被判失败、
MCAP 通道产出的根本不是二进制 MCAP。

**"0/8"必须拆开看（v1.1 修正）**：其中 **5 处是"未送达"**——故障注在 `cam_front`（4 处）
与 `cam_wrist`（1 处），而导出后的 LeRobot 数据集只含 `actions`/`robot_state`/`tactile`
与 4 个记账字段，**相机流一条都没进去、视频文件数为 0**，physlint 根本没收到这些故障；
另外 **3 处是"已送达但未检出"**（`robot_state` 的 `clock_drift` 与 `missing_interval`、
`tactile` 的 `non_monotonic`）。把两者混为一谈，会同时高估算法缺陷、低估交接缺陷。
详见 `docs/toolchain-integration-matrix.md` §0.1。

由此识别出**本次所测工具链的三个待解决问题**，它们是当前阶段的切入点：

1. **交接测量不足**——所测配置出现丢流、命名不匹配、容器不通。
2. **统一口径不足**——所测输出格式、严重度语义、退出码需要显式映射。
3. **下游影响未验证**——"清洗到底有没有让下游模型变好"连可靠前提都没有；
   注意**相关不等于因果**，结论只能来自受控实验（见 §11）。

见 §2.2 与 `docs/toolchain-integration-matrix.md`。关键结论：**所测配置存在交接损失，

## 7. 技术架构与数据流

```
数据源  LeRobot v3（主）· TUM RGB-D（辅）· embodied-sync run · Open X-Embodiment
          │
          ▼  adapters/            FR-06：保住全部流（含视频）★实测缺口在这
          │
          ▼  schema · sync · quality · geometry      MVP 1 已实现
          │
          ▼  编排层 orchestrator   调用 physlint / embodied-sync，收集原始输出
          │
          ▼  findings.py          FR-07：统一 finding schema（本项目核心差异点）
          │
          ▼  报告层 report        FR-08/10：JSONL / Markdown / 检出矩阵
          │
          ├─ export/lerobot_v3    FR-09：含视频的合规导出（交接保真修复）
          ├─ Evaluation           FR-11：预注册 + 下游策略效果
          └─ interfaces/          FR-12/13：处理后的数据 API +（可选）MCP
```

**四条已定技术决策：**

1. **交接保真：先测后补。** 先量化损失，再补最小可用的 LeRobot 视频导出。
   只测不补拿不到"能跑的系统"，只补不测丢掉最有价值的发现。
2. **集成优先于自研。** 任何新功能先问：现成工具做了没有？做了就调用。
3. **处理后数据服务与交接契约必须交付。** 报告层提供并行诊断，不能替代数据产出。
4. **原始数据只读。** 派生处理允许写新目录，并记录源引用、参数与处理版本。

## 8. 数据与数据集

**数据集是"图片和数字绑在一起"的多传感器记录**，不是单纯图片，也不需要视觉识别模型——
当前图像检查仅实现解码、格式和尺寸校验；模糊、黑帧、过曝检测尚未实现。
现有几何投影和适配器使用 CPU；未来可以按需接入现成视觉模型，保留模型无关的核心。

公开数据集分四类：

| 类型 | 例子 | 本项目用途 |
|---|---|---|
| 机器人学习数据集 | LeRobot（PushT / SO-101）、Open X-Embodiment | **主线**（图像+状态+动作对齐） |
| 经典视觉/几何数据集 | TUM RGB-D、EuRoC、KITTI | **辅助**（验证几何计算） |
| 现场录制日志 | MCAP、rosbag | 竞品工具的主要输入 |
| 故障/基准数据集 | VisionFault-350K | 后续评测素材 |

实测提示：physlint 跑过 4 个公开 LeRobot 数据集全零缺陷，但另 10 个快照只有 5 个通过默认契约——
**公开数据集里既有干净的也有带问题的**，这既是工具存在的理由，也是实验的现成素材。
起点明确：**LeRobot 的 PushT**（数据小、图像状态动作齐全、有现成评估流程）。

## 9. 开发流程与工程纪律

1. 用 `uv` 管理依赖（`./dev.ps1`），提交前跑 `pytest`、`ruff check`、`ruff format --check`。
2. `data/`、`outputs/`、`dist/`、`.venv*` 不入库；保留源时间戳、单位、标定 ID 与原始文件。
3. 合成数据与估算值必须显式标注；报告真实测量结果，未实现的模块必须明确说明。
4. 核心不依赖 Rerun / ROS / GPU；不提交环境、凭据、个人机器路径。

## 11. 下游影响验证与预注册模板（跑实验之前必须提交）

**先限定一个容易被夸大的地方：数据质量指标与任务成功率之间出现相关，并不能单独证明因果关系。**
人工故障注入、固定模型、控制训练条件是目前最合理的起点，但结论只能来自受控实验的比较，
并且必须报告效应量与置信区间。相关性强弱只作线索，不能当作"清洗有用"的证明。

用 Git 提交时间戳证明预注册先于实验。缺少预注册的结果不得用于任何结论。

```
实验编号：
假设：上游质量指标能预测下游策略性能退化，且预测力强于"训练数据量"这一简单基线。
自变量：故障类型（dropped_frames / clock_drift / jitter / missing_interval）
        × 严重度 5 档（clean / 轻微 / 中等 / 严重 / 极严重）
因变量：任务成功率（固定测试 episode 数）、训练步数、推理时延
控制变量：策略架构、超参、训练步数、随机种子（每档 ≥3）、硬件
比较组：clean / corrupted-unprocessed / corrupted-processed；过滤时增加等样本量基线
判定阈值（先说死）：
  - 成立：严重档成功率相对 clean 下降 ≥15 个百分点，且质量指标与成功率的 Spearman ρ ≥ 0.7
  - 下降 <5 个百分点：只支持本设置下对该故障不敏感，不等于清洗没有价值
  - 处理收益：另比较 corrupted-processed 与 corrupted-unprocessed，预注册效应量和区间
必须报告：失败与无显著差异的结果、每个 seed 的原始数据、机器可读 CSV、效应量与置信区间
禁止：事后挑选指标、事后剔除 seed、只报告最好的一组
公平性：若本方法使用了额外传感器信息，必须另设获得相同信息的基线，
        否则不得把收益归因于本项目的处理流程。
```

## 12. 创新点与差异化

创新不在算法新，而在**回答没人回答过的问题**。三个方向都不需要大算力，失败也是有效结论：

1. **质检工具到底靠不靠谱？** 做公开、可复现的"质检工具评测基准"：同一份数据注入已知故障，
   横向比较检出率/漏报率/误报率。这是唯一能积累的护城河——**基准和引用是复利，功能不是**。
   评测必须把"未送达（交接丢失）"与"已送达但漏检（算法缺陷）"分开报告。
2. **查出的问题重不重要？** 用受控实验量化"缺陷严重度 → 模型性能下降"的映射；
   相关只作线索，因果结论必须来自受控比较。
3. **接了工具的 agent 诊断准不准？** 人工标注坏数据，比对 agent 的定位/归因/建议是否可靠。

优先交付数据消费接口，再做可复现的工具链验证；是否有研究新意需独立检索，不宣称领域空白。

## 16. 诚实评估

**实用性**：有，属于"省时间"型，不是"非你不可"型。真实痛点存在，但工程师默认自己写脚本解决；
价值在于把事情规范化、可复现、出正式报告。最直接的证据是实测：现成工具连"发现问题"都没做好。

**能否交付**：作为个人项目（毕设/作品集/开源仓库）**能**，范围已收到一条链路，十到十一周可完成，
主要风险是范围膨胀和训练实验超算力。作为商业产品**不能"顺利"交付**：付费方不明确、需行业人脉、
竞品虽小但存在、长期维护成本挂身。这是商业结构问题，与技术无关。

**选题状态**：技术侧**通过**（有实测支撑，不是推测）；需求侧**未验证**（客户访谈数 = 0）。
对路线甲这不阻塞，但它决定了 Evaluation 该回答谁的问题。

**创新空间**：见 §12。核心判断——检查器已经拥挤，证据才是稀缺品。
